# STEP 3: GENERATION RULES — MUST FOLLOW ALL

## RULE 1: Ordering of evidence (match the narrative to STEP 2 section order)
1. After intro/context, present **mileage_list** items in the order given (already sorted by semester, then category).
2. Then **activities** in the order given (chronological by start date).
3. Then **github_repos** in the order given (newest `updated_at` first when present).
4. **Tech stack** and **bio** support the story; do not reorder STEP 2 blocks when quoting structure.

## RULE 2: Honest reflection (not resume hype)
- Describe what the data actually shows: what they did, what they likely learned, where evidence is thin.
- Do **not** use recruiter-style puffery or the "language calibration" rewrite table from sales CVs.
- **Banned without proof:** phrases like "깊은 이해", "풍부한 경험", "탄탄한 역량", "뛰어난", "탁월한" unless the **same sentence** cites a concrete fact from STEP 2 (repo name, activity title, award name, or tool used in a named project).
- **Strengths / 강점 섹션:** Each strength bullet (or paragraph) must **cite at least one** line from `[activities]` or `[github_repos]` — e.g. activity title in parentheses or a quoted repo name. If you cannot tie a strength to STEP 2, **omit** that bullet.

## RULE 3: Gaps and growth (evidence-bound)
- Call out **gaps** only from what is missing, empty, or weak in STEP 2.
- Suggest **growth areas** as concrete, student-appropriate next steps — not invented achievements.
- **No generic-only advice.** Do not write stand-alone lines like "AWS를 더 공부하세요" that apply to anyone. Tie every growth item to STEP 2: e.g. if `[tech_stack]` shows AWS at NN% but `[github_repos]` / activities rarely mention deployment/infra, say that **comparison explicitly**, then suggest infra-facing evidence (portfolio project, IaC, etc.).
- Each gap/growth bullet should imply **what evidence was checked** (tech_stack vs repos vs activities).

## RULE 4: Zero fabrication
- Never invent metrics, employers, awards, or repos not in STEP 2.
- If a section has no lines, omit it or note clearly that nothing was selected.

## RULE 5–8 테마 (Portfolio HTML 무결성 — 아래 번호 규칙과 함께)
1. **Tech stack 시각화:** RULE 6 — 모든 NN% 유지·가시화.
2. **중복 활동 병합:** RULE 5 — 유사 활동 단일 카드.
3. **Repo 해석 깊이:** RULE 7 — 기간·팀·역할·기여 라인 전부 노출(존재 시).
4. **강점 근거:** RULE 2·8 — 강점마다 활동/레포 제목 인용.

## RULE 5: Duplicate activities (`[activities]`)
- If two or more entries are clearly the **same project/topic** (same title after trimming case-insensitive, or overlapping distinctive keywords + same role), **merge** into one narrative card/timeline row: combine periods or show both ranges once — **do not** show two identical cards side-by-side.
- When unsure, prefer **one** consolidated entry over duplication.

## RULE 6: Tech stack percentages (`[tech_stack]`)
- Lines often look like `- Skill (domain) NN%`. Preserve **every NN%** present in STEP 2 in the rendered HTML (sidebar pills, Tech Evidence table, progress bars, or explicit text like `Java 70%`). **Do not drop** numeric levels.

## RULE 7: GitHub repos depth (`[github_repos]` detail lines)
- Mirror CV/recruiter RULE 7: when STEP 2 lists **기간**, **팀 구성**, **내 역할**, **주요 기여** under a repo, those lines **must** appear in HTML as bullets or sub-blocks; skip lines that do not exist (no placeholders).

## RULE 8: Strength citations (explicit)
- Restates RULE 2: each reflective strength bullet cites ≥1 concrete STEP 2 title from `[activities]` or `[github_repos]` by name in the same bullet or sentence.

## RULE 9: 링크 처리
- `[github_repos]`에 `· URL:` 이 있으면 제목을 `<a href="[url]" target="_blank" rel="noopener noreferrer">[제목] ↗</a>` 로 렌더링.
- `[contact]` GitHub → `<a href>` (새 탭), Email → `<a href="mailto:">`.
- `[activities]`에 `· URL:` 이 있으면 동일 `target`/`rel`로 링크화.

## RULE 10: 설명 자동 개선 (activity / repo)
- `· 설명:` + `· tags:`(또는 `· 기술:`)만 참고해 **1–2줄**로: "[기술명]을 활용해 [기능/역할] 구현" 형식.
- 원본·tags에 없는 기술·사실·수치는 추가 금지. 톤은 성찰형이되 과장 없이.
